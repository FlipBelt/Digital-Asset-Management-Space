# 系统逐项排查修改计划

> 实施状态（2026-08-10）：本计划的基础治理能力已完成并部署。已上线规则化内部编号、统一标识索引、归属范围、专属资料模板、关系白名单与资产详情交互；生产存量 29 项在用资产已完成内部标识补全。费用报销与付款方式的独立财务治理仍按原计划留待后续模块实施。

> 本文用于逐项审计现有系统并记录后续修改方案。当前阶段只规划，不实施、不部署。

## 已确认的总体决策

1. 专属资料由管理员按资产类型统一配置模板，资产负责人填写实例值；不允许每项资产自由发明字段。
2. 归属范围、负责人和使用人员是核心治理字段；归属范围明确区分待确认、公司级和部门级。
3. 关联资产按上游、下游、同级三个观察方向操作，具体关系由双方对象类型和关系规则自动收敛。
4. 每项正式资产必须有规律、稳定、可读的内部资产编号；资产名称允许重复。
5. 平台原生标识为可选项，平台没有提供时不强制填写，不影响资产正式登记和内部区分。
6. 历史来源编号继续保留用于追溯，但默认缩略或收起，不占据主要业务视图。
7. 六类核心对象及注册身份辅助层均使用“名称 + 内部编号/类型 + 上下游关键上下文”的展示方式。

## 1. 资产详情：专属资料模板

### 现状

- 数据库已有资产类型字段定义 `AssetFieldDefinition` 和资产字段值 `AssetFieldValue`。
- 后端已有字段模板查询、新增字段和字段值保存接口。
- 管理员控制台目前只能新增资产类型，没有字段模板管理界面。
- 资产详情已经读取字段定义和值，但除“自研系统”固定模板外，尚未动态渲染专属资料表单。
- 页面“可由管理员添加扩展字段模板”的提示目前没有形成可操作闭环。

### 修改方案

1. 在“管理员控制台 → 分类与规则 → 资产类型”增加“专属资料模板”配置入口。
2. 支持字段分组、字段类型、必填、选项、单位、校验、排序、敏感级别、搜索能力和完整度权重。
3. 资产详情“专属资料”按资产类型模板自动渲染，由资产负责人填写具体值。
4. 内置注册身份、云服务器、云数据库、SaaS订阅、API服务、域名和自研系统标准模板。
5. 支持“通用类型模板 + 平台差异模板”，例如“云服务器 + 阿里云 ECS 扩展字段”。
6. 模板变更必须版本化；停用字段不删除历史值。
7. 密码、API Secret、私钥和恢复码不得保存为普通字段，只保存外部安全系统引用。

### 建模原则

- CPU、内存、地域、IP、实例 ID 等描述性数据作为专属字段。
- 具有独立生命周期、负责人或关系的数据建成独立资产，例如业务系统、数据库、重要备份等。
- 不允许每项资产自由发明字段；管理员定义统一模板，资产负责人填写字段值。

## 2. 资产详情：归属、负责人、使用人员与权限隔离

### 现状

- 页面已有“归属组织、负责人、使用人员”三个业务字段。
- `owner_department_id` 为空时，当前页面有时显示“公司主体”，有时显示“待补充”，同一个空值承担了两种含义。
- 选择负责人不会自动带出该人员的主部门，归属组织和负责人完全独立填写。
- 负责人必填后才能把草稿确认为正式资产；使用人员可为空。
- 公司级资产不属于任何部门；部门主管不会因部门范围自动看到它，但资产负责人和使用人员仍可看到。

### 现行权限规则

1. 系统管理员、资产管理员可以查看和管理公司全部资产。
2. 审计人员可以查看公司全部资产，但不能修改。
3. 部门负责人可以查看所管部门及下级部门归属的资产。
4. 负责人和使用人员可以查看分配给自己的资产。
5. 创建人当前会一直保留查看权限，即使资产之后已正式确认或重新分配。
6. 归属部门和负责人变更由资产管理员，或当前归属部门范围内的部门负责人执行。
7. 当前普通员工角色没有 `asset.write` 权限，因此普通员工即使是负责人，也可能无法按原设计维护资产资料。

### 修改方案

1. “归属组织”继续作为系统核心字段，不能改成自定义字段，因为权限隔离直接依赖它。
2. 明确区分三种归属状态：`待确认`、`公司级`、`部门级`；部门级必须选择部门，公司级允许部门为空。
3. 选择负责人时读取其主部门：如果归属尚未填写，默认建议该主部门；用户可以改为公司级或其他有权选择的部门。
4. 负责人变更后不静默改变已确认的归属部门，只提示“负责人部门与资产归属不同”，由有治理权限的人确认是否同步。
5. 在资产类型上配置默认归属策略：公司级优先、负责人主部门优先、必须手工选择。平台企业账号可默认公司级，云服务器可默认负责人主部门。
6. 公司级资产由资产管理员治理；其负责人可以维护专属资料和日常信息，使用人员只读。
7. 部门级资产由资产管理员或对应部门负责人治理；负责人维护资料，使用人员只读。
8. 修正负责人写权限，使“负责人可维护自己负责的资产”与权限文档一致，同时仍由后端资产范围约束，不能修改其他资产。
9. 创建人可见性只用于草稿和待确认阶段；资产正式确认后，访问权应由归属、负责人和使用人员决定，避免创建人永久越权。
10. 所有归属、负责人和使用人员变更继续保留审计记录，并在跨部门调整时生成明确的变更摘要。

### 推荐页面交互

- 归属范围：待确认 / 公司级 / 部门级。
- 归属部门：仅选择“部门级”时显示并必填。
- 负责人：单选，显示人员所属主部门。
- 负责人选定且归属待确认时，提示“一键采用负责人主部门”。
- 使用人员：多选；负责人默认拥有管理和使用权，无需重复选择。
- 权限说明：在表单旁直接显示当前选择将产生的查看、维护和治理范围。

### 待实施验收重点

- 公司级平台不选部门时，资产管理员、负责人和使用人员能按规则访问，普通部门主管不能自动越权查看。
- 部门级服务器默认建议负责人主部门，并允许有权限的人调整。
- 负责人是普通员工时，可以维护自己负责资产的基础资料和专属资料，但不能变更归属和负责人。
- 创建人在资产转正并移交后，不再因创建行为永久保留访问权。
- API 直接访问与页面显示遵循同一权限规则。

## 3. 资产详情：关联资产与关系方向

### 现状与根因

- 当前关系表以 `source_asset_id + relation_type + target_asset_id` 保存一条有方向的关系。
- 现有试点数据的规范方向本身基本正确，例如：
  - `集团账号管理中台 --DEPLOYED_ON--> 阿里云 ECS`；
  - `阿里云 ECS --PURCHASED_VIA--> 阿里云技术使用主体`。
- 资产详情页却简单地把“当前资产是 source”显示成“下游”，把“当前资产是 target”显示成“上游”。这个判断与大部分关系谓词的语义相反，因此截图中两条关系均被标错方向。
- 新建关系接口始终把当前页面资产保存为 source，无法从当前资产页面正确建立“某系统部署在当前服务器上”这类反向关系。
- 目标资产下拉框列出所有可见资产，没有按当前资产类型、关系方向和目标类型过滤。
- 关系下拉框固定列出全部关系，允许形成语义不合法的组合。
- 正向和反向只使用同一个显示词。例如 `系统 --DEPLOYED_ON--> 服务器`，在系统侧应显示“部署在”，在服务器侧应显示“承载系统”，不能都显示“部署在”。
- 关系编码同时存在大小写形式，可能造成语义重复和重复建边。
- 后端建立关系时只校验当前资产的维护权限，没有完整校验目标资产的可见性、类型兼容性和跨权限域规则。

### 关系模型原则

1. 上游、下游、平级是“从当前资产观察的方向”，不是数据库中的关系类型。
2. 数据库存储规范化的语义边：`主语资产 --关系谓词--> 宾语资产`。
3. 每个关系定义同时配置正向标签和反向标签。
4. 每个关系定义配置允许的源资产类型、目标资产类型、基数限制和是否影响资产地图。
5. 页面不要求使用者理解 source/target；后端根据当前资产、观察方向和关系规则自动确定规范存储方向。

### 第一批关系规则

| 规范关系 | 允许的典型类型 | 正向显示 | 反向显示 |
| --- | --- | --- | --- |
| `REGISTERED_BY` | 平台账号/租户 → 注册身份 | 注册身份为 | 注册了/用于注册 |
| `PURCHASED_VIA` | 服务、云资源 → 平台账号/租户 | 购买自 | 购买/开通了 |
| `DEPLOYED_ON` | 自研系统、应用 → 云服务器/运行环境 | 部署在 | 承载系统 |
| `CALLS` | 系统、工作流 → API服务 | 调用 | 被调用 |
| `USES` | 系统、人员使用对象 → 服务/资源 | 使用 | 被使用 |
| `STORED_IN` | 数据、备份 → 数据库/存储资源 | 存储在 | 存放了 |
| `DEPENDS_ON` | 系统/资源 → 被依赖资产 | 依赖 | 被依赖 |
| `BILLED_TO` | 服务/资源 → 费用归集对象 | 费用归集到 | 承担费用 |
| `REPLACES` | 同类资产 → 被替代资产 | 替代 | 被替代 |

### 推荐页面结构

1. 关系列表改成三个明确分区：
   - 上游/来源：当前资产购买自、注册于、部署在、依赖或存储于哪些资产；
   - 下游/使用方：哪些系统、服务或资源部署在、调用、使用或依赖当前资产；
   - 同级/演进关系：替代、镜像、同步等非层级关系。
2. 不再提供“任意资产 + 全部关系”的通用表单，改为“添加上游”“添加下游”“添加同级关系”三个入口。
3. 选择方向后，只显示与当前资产类型兼容的目标资产，并按类型分组、支持搜索。
4. 选择目标资产后，根据双方资产类型自动确定唯一关系；如果确有多个合法关系，只显示少量合法选项。
5. 从下游入口建立关系时，由后端自动反转 source/target，用户不接触技术方向。
6. 关系卡片使用自然语言显示，并明确写出完整语句，避免只有“上游/下游 + 一个关系词”。

### 示例：阿里云 ECS

从“阿里云 ECS”详情观察：

- 上游/来源：`购买自 → 阿里云技术使用主体`；规范存储为 `ECS --PURCHASED_VIA--> 平台使用主体`。
- 下游/使用方：`承载系统 → 集团账号管理中台`；规范存储为 `集团账号管理中台 --DEPLOYED_ON--> ECS`。

因此截图中的数据边不需要为了显示而全部反转，首先应修正页面的观察方向与反向关系标签。

### 后端与管理员配置

1. 在“管理员控制台 → 分类与规则 → 关系规则”增加关系定义管理入口。
2. 核心关系规则由系统内置并保护；管理员可以启停、配置自定义资产类型兼容关系，但不能破坏核心语义方向。
3. 新建关系接口接收“当前资产、观察方向、目标资产、关系意图”，由后端规范化 source/target 并校验类型。
4. 对两端资产同时执行可见性与权限检查；跨部门或跨隔离范围关系按规则要求资产管理员确认。
5. 统一关系编码大小写，防止 `CALLS` 与 `calls` 被视为不同关系。
6. 删除关系时校验两端权限、关系来源和操作角色；自动同步关系不能被普通负责人直接删除。
7. 资产地图、资产详情和导入程序共用同一套关系定义和正反向标签。

### 数据核验与迁移

1. 发布前审计所有现有关系，按源类型、关系类型、目标类型输出异常清单。
2. 对语义正确但页面显示相反的关系只修显示，不改数据方向。
3. 对确实建反或类型不兼容的关系生成迁移预览，人工确认后再修复。
4. 修复后重新验证老板导入数据、试点 ECS、自研系统和资产地图的完整链路。

### 待实施验收重点

- ECS 页面正确显示“上游：购买自阿里云账号”和“下游：承载集团账号管理中台”。
- 从 ECS 页面添加下游系统时，只出现可部署的系统类资产，并自动建立 `系统 --DEPLOYED_ON--> ECS`。
- 从 ECS 页面添加购买上游时，只出现合法的平台账号/租户，关系自动为 `PURCHASED_VIA`。
- 不允许创建“注册身份部署在SaaS服务”等不合法组合。
- 同一条关系在两端详情页使用正确的正向/反向自然语言。
- 无权查看目标资产的用户不能通过 UUID 建立关系或探测目标资产。

## 4. 资产概览：名称、内部编号与多来源唯一标识

### 现状

- 资产名称 `name` 是使用者可修改的展示名称，不要求唯一。
- 资产表已有独立字段 `asset_code`，在同一公司主体内唯一；资产详情标题上方已经显示该编号。
- 普通登记未填写编号时，系统生成随机形式 `AST-XXXXXXXXXX`；试点数据使用人工预置的 `PILOT-...` 编号。
- `asset_code` 当前不能通过普通资产编辑接口修改，具备一定稳定性，但编号规则没有按资产类型统一规划。
- 云资源已有 `external_identifier_type/value`，可保存阿里云 ECS 实例 ID 等平台原生标识，但只存在于 `ResourceProfile`，资产概览没有统一展示。
- 老板旧系统的 `SUB-001`、`API-005`、`DD-...` 等来源编号保存在导入暂存记录 `SourceImportRecord.source_identifier` 中，并关联了正式资产，但没有作为正式资产标识展示和搜索。
- 当前列表搜索主要覆盖资产名称和 `asset_code`，没有统一覆盖平台实例 ID、旧系统 ID 和其他别名。
- 因缺少上下文展示，现有名称被迫写入“客服部门使用主体、技术使用主体、待补充实例 ID”等信息，名称承担了过多区分职责。

### 标识分层原则

每项资产同时允许存在四类标识，各司其职：

1. **系统主键 UUID**：数据库内部技术标识，永久不变，默认不向业务用户强调。
2. **内部资产编号 `asset_code`**：公司内部稳定、人类可读的资产身份证，系统生成、不可重复、归档后不复用。
3. **平台原生标识（可选）**：阿里云实例 ID、Workspace ID、租户 ID、Bucket 名称等；平台提供时登记，平台没有或暂时未知时允许留空。
4. **来源系统/历史编号（辅助）**：老板旧系统的 `SUB-001`、`API-005`、`DD-004` 等，原样保留用于核对和追溯，但默认不作为主展示信息。

资产名称只负责“让人看懂”，不承担唯一性。归属部门、平台账号、负责人等信息通过结构化字段和关系展示，不编码进名称。

### 内部资产编号方案

1. 按资产类型配置稳定前缀并由系统顺序生成，例如：
   - 注册身份：`REG-000001`；
   - 平台账号/租户：`ACC-000001`；
   - SaaS订阅：`SUB-000001`；
   - API服务：`API-000001`；
   - 云服务器：`ECS-000001`；
   - 自研系统：`SYS-000001`。
2. 多法人主体场景可在展示编号中增加稳定的公司编码，例如 `FB-ECS-000001`。
3. 编号创建后不因改名、换负责人、换部门或换账号而改变。
4. 普通用户不能手工修改内部编号；确需纠错时由资产管理员执行并记录编号变更历史和旧编号别名。
5. 资产归档后编号永久保留，不分配给新资产。
6. 正式资产必须生成内部编号；平台实例 ID 和历史编号是否存在，不影响内部编号生成。

### 多标识索引模型

新增统一的资产标识记录，而不是继续把不同标识散落在各类专属资料中。每条标识至少包含：

- `asset_id`：关联正式资产；
- `namespace/source_system`：例如 `internal`、`aliyun`、`flipbelt_ai_v4`；
- `identifier_type`：例如 `asset_code`、`ecs_instance_id`、`legacy_service_id`；
- `identifier_value`：真实标识值；
- `is_primary`：是否作为该资产的主要外部标识；
- `verification_status`：待核验、已核验、失效；
- `first_seen_at/last_verified_at`：发现和核验时间；
- `source_import_record_id`：如来自导入，保留原始记录追溯；
- `confidentiality`：标识的展示和导出级别。

唯一性按标识命名空间确定：

- 内部资产编号在公司主体内唯一；
- 阿里云 ECS 实例 ID 在阿里云命名空间内唯一；
- 老板旧系统 ID 按“来源系统 + 来源对象类型 + 原编号”唯一；
- 空白或待补充的外部标识不参与唯一约束，但资产仍有内部编号可区分。

### 推荐页面展示

资产详情概览顶部改成：

```text
阿里云 ECS
内部编号：ECS-000002
平台实例：待补充 / i-bp******
购买账号：阿里云技术使用主体
归属范围：技术部或公司级
历史编号：如有则显示来源标签
```

列表和搜索结果采用“名称 + 内部编号 + 关键上下文”的三行信息，不再强迫名称包含括号说明：

```text
阿里云 ECS
ECS-000002 · 阿里云技术使用主体
技术部 · 实例 ID 待补充
```

平台原生标识不存在时不显示空白字段；需要核验时才显示“实例 ID 待补充”的待办标签。历史来源编号默认以折叠标签展示，例如“历史标识 1 项”，展开后再显示来源系统和原编号。

### 六类对象的上下文展示规则

名称和编号只解决“它是谁”，界面还必须展示它在六层关系中的位置。不同对象显示不同的关键上下文：

| 对象层 | 第一行 | 第二行 | 第三行关键上下文 |
| --- | --- | --- | --- |
| 公司主体 | 公司名称 | 公司编码、状态 | 下辖平台数、资产数 |
| 平台 | 平台名称 | 平台类型、供应商 | 公司账号数、服务数 |
| 注册身份辅助层 | 身份名称 | `REG-*`、身份类型 | 注册了哪些平台账号、保管人 |
| 平台账号/使用主体 | 账号名称 | `ACC-*`、所属平台 | 注册身份、下辖服务/资源数、归属范围 |
| 服务/资源 | 资源名称 | `SUB/API/ECS-*`、资源类型 | 购买账号、归属组织、平台原生标识（如有） |
| 自研系统 | 系统名称 | `SYS-*`、系统类型 | 部署资源、调用服务、归属组织 |
| 人员 | 人员姓名 | 员工编号、部门 | 负责资产数、使用资产数；不生成资产编号 |

处于中间层的平台账号/使用主体需要同时展示多层信息，例如：

```text
阿里云技术使用主体
ACC-000003 · 阿里云
注册身份：技术专用手机号 · 下辖：4 项资源 · 公司级
```

关系选择器、资产地图、资产列表和搜索结果共用这套摘要组件，确保用户在任何位置都能看到对象类型和必要的上下游上下文，而不是只看到一个名称。

### 名称与编号规则

- 名称允许重复，例如多台资产都可以叫“阿里云 ECS”。
- 界面通过内部编号、平台实例 ID、购买账号和归属组织区分同名资产。
- 创建同名资产时不阻止，但应提示可能重复，并展示已有资产的编号和上下文。
- 一旦补充平台实例 ID，系统必须检查是否已经绑定其他资产，避免重复登记同一实例。
- 资产地图、关系选择器、导入预览和导出文件都同时显示名称与内部编号。

### 老板旧系统数据迁移

1. 从已保存的 `SourceImportRecord` 提取 `SUB/API/DD` 等旧系统 ID，写入正式资产标识索引。
2. 旧系统 ID 原样保留为“FlipBelt AI v4 来源编号”，不直接覆盖内部资产编号，避免不同来源发生编号冲突。
3. 历史编号默认缩略为“历史标识 1 项”；在追溯、导入核对和高级搜索场景展开后显示，例如“FlipBelt AI v4 / SUB-003”。
4. 导入记录继续保留原始数据指纹和 `canonical_asset_id`，以支持从正式资产追溯到原始 HTML/JSON 记录。

### 数据清理与兼容

1. 盘点现有 `AST-*`、`PILOT-*` 和手工编号，生成编号迁移预览，不直接覆盖。
2. 对需要统一编号的资产生成新编号，并把原编号保留为别名；已有链接仍使用 UUID，不受编号变化影响。
3. 将 `ResourceProfile.external_identifier_*` 和租户标识迁移/同步到统一标识索引，专属资料中仍可展示但不重复保存两个真值来源。
4. 清理名称中的“客服部门使用主体、技术使用主体、待补充实例 ID”等结构化描述前，必须先确保账号关系、归属和标识已正确入库。

### 待实施验收重点

- 两台都叫“阿里云 ECS”的服务器能通过不同内部编号、账号、部门和实例 ID 清楚区分。
- 实例 ID 尚未补充时，内部编号仍能稳定定位资产。
- 老板旧系统 `SUB/API/DD` 编号可以在资产详情、搜索和导出中找到对应正式资产。
- 同一个阿里云实例 ID 不能绑定两个有效资产。
- 改名、换负责人、换部门不改变内部编号。
- 名称搜索、内部编号搜索、平台实例 ID 搜索和历史编号搜索都遵守资产权限隔离。

## 总体实施顺序

### 阶段 A：数据与规则基座

1. 建立归属范围字段，区分待确认、公司级和部门级。
2. 建立统一资产标识索引、内部编号生成规则和编号序列。
3. 建立关系定义规则，包含源类型、目标类型、正反标签、方向和基数限制。
4. 扩展专属资料字段模板元数据，包括分组、校验、敏感级别和完整度权重。
5. 所有数据库变更使用可回滚迁移，不直接重建现有数据表。

### 阶段 B：后端治理与权限

1. 实现规律化内部编号自动生成、编号占用和归档不复用。
2. 实现多来源标识登记、查重、搜索和权限过滤。
3. 重构关系创建接口，由后端根据观察方向和规则规范化 source/target。
4. 修复负责人写权限、创建人永久可见和公司级/部门级治理规则。
5. 专属字段保存按模板执行类型、必填和权限校验。

### 阶段 C：管理员配置

1. “分类与规则 → 专属资料模板”：配置资产类型字段。
2. “分类与规则 → 关系规则”：配置类型兼容和正反向标签。
3. “分类与规则 → 编号规则”：查看各类型前缀和下一个编号，只允许受控调整。
4. “分类与规则 → 归属规则”：配置公司级优先、负责人部门优先或必须手工确认。

### 阶段 D：资产详情重构

1. 概览：展示名称、内部编号和分层上下文，平台原生标识按需显示，历史编号默认收起。
2. 专属资料：按模板动态渲染并计算资料完整度。
3. 责任人员：明确归属范围，负责人部门仅作为建议，不静默改变已确认归属。
4. 关联资产：分上游、下游、同级展示，目标和关系按类型自动过滤。
5. 变更历史：显示编号、归属、负责人、关系和字段模板的可读变更摘要。

### 阶段 E：现有数据整理

1. 输出所有现有资产的编号、外部标识、历史编号、归属和关系审计清单。
2. 为缺少规律编号的资产生成迁移预览，原编号保留为别名。
3. 把老板旧系统 `SUB/API/DD` 编号接入正式标识索引并默认折叠展示。
4. 区分关系“显示反向”和“数据建反”，只修真正有问题的数据。
5. 在结构化归属、账号和标识完整后，再清理资产名称中的括号说明。

### 阶段 F：统一验收与发布

1. 使用两台同名 ECS、多个同平台账号、多个服务实例和跨部门负责人构造验收场景。
2. 验证资产列表、详情、地图、关系选择器、搜索、导入和导出使用同一摘要与标识规则。
3. 验证管理员、资产管理员、部门负责人、负责人、使用人员和审计人员的权限矩阵。
4. 执行自动化测试、迁移检查、生产构建和大数据量关系视图测试。
5. 生产发布前完成数据库、后端和前端备份；分阶段发布并保留回滚版本。
