# 产品方向调整实施规划：实例化模型与多视图展示

## 一、目标

将集团账户管理中台从“强制补齐 L1-L6 的层级录入工具”调整为：

> 每个来源实例先判断自身层级；关系按证据和人工确认逐步连接；前端按使用场景展示，而不是强迫所有人先理解六层模型。

本规划先完成后端数据模型和接入规则，再进行前端整体改造。

## 二、已确认的产品原则

1. L1-L6 是管理坐标，不是强制父子链路。
2. L2 表示注册、登录、恢复和管理身份，包括邮箱、手机号、用户名、管理员账号和子账号身份。
3. L3 表示平台目录。
4. L4 只在存在企业租户、商户号、主账号、工作区或其他明确平台公司账户证据时建立。
5. L5 只在存在明确的人员、对象和权限关系时建立。
6. L6 统一承载订阅、API、应用、SaaS、店铺、云资源、VPN、邮箱和业务环境等具体实例，并通过子类型区分。
7. 原始资料必须先进入资料接入池；候选对象和关系经人工确认后才能升级为正式资产。
8. 关系未知是正常状态，不是录入错误；系统不得为了完整链路自动猜测。
9. 密码、API Key、Cookie、PIN、验证码等只保留外部受控密码库引用，不复制明文。

## 三、当前问题与处理边界

### 已解决的模型方向

- 普通账号不再自动生成 L4。
- L2、L3、L6 可以独立存在。
- L6 支持订阅、API、应用和资源等不同类型。
- 平台与 L2/L6 之间支持可选直接关联。
- 候选对象、候选关系和审核记录有独立承载位置。

### 尚未完成的工程工作

- 新后端代码尚未部署到生产环境。
- 新增的可选平台关联表需要执行数据库迁移。
- 导入规划器需要全面按“普通账号=L2、明确租户才是 L4 候选”规则回归验证。
- 资料接入池仍需补充按来源文件展开原子实例的正式接口和审核动作。
- 当前前端仍以六层规划表为主，业务视图和老板台账兼容视图尚未整体改造。

## 四、实施阶段

### 阶段 1：后端模型和规则收口

目标：保证数据可以真实表达“不完整关系”和“独立实例”。

工作内容：

- 固化 L2、L3、L4、L5、L6 的对象边界和子类型字典。
- 保证 L2、L6 在公司主体未知时也能暂存。
- 保证 L4 仍要求公司主体和平台证据。
- 增加或完善 L2/L3、L6/L3 的可选关联。
- 导入规划器禁止从邮箱、手机号、用户名、普通账号字段推导 L4。
- 为订阅、API、应用、SaaS、资源、环境等 L6 类型定义字段模板。
- 所有候选对象和关系保留来源记录、置信度、审核状态和审核备注。
- 对导入预览和 AI 分析输入统一做敏感字段脱敏。

验收条件：

- 候选资料可以只有 L2、L3 或 L6，不会因缺少 L4/L5 被拒绝。
- 普通“账号”不会自动生成公司平台账号。
- L6 可以直接关联 L3，也可以在确认后关联 L4。
- 候选关系不等于正式关系。
- 现有 MiniMax、DeepSeek 等人工资产不受影响。

### 阶段 2：资料接入池和导入预览

目标：把老板台账和阿里云文件转成可审阅的原子实例。

展示字段：

- 来源文件；
- 来源记录或原始编号；
- 脱敏后的原始事实；
- 建议层级和 L6 子类型；
- 已知平台关系；
- 已知身份关系；
- L4/L5 是否缺失；
- 风险和待确认事项；
- 当前状态：待确认、已确认、历史保留或不接入。

导入原则：

- 老板台账的订阅、API、钉钉应用作为 L6 候选；
- 邮箱、手机号和登录身份作为 L2 候选；
- 平台目录作为 L3 候选；
- 员工与“使用人”只形成 L5 候选关系；
- 流水、报销、付款和月度汇总只保留为历史证据；
- 阿里云每个文件拆成多个原子实例，不按文件整体生成资产。

### 阶段 3：后端确认升级和审计

目标：让用户可以逐项确认，而不是批量猜测。

每次确认必须记录：

- 来源记录 ID；
- 候选对象 ID；
- 最终层级和对象类型；
- 是否匹配已有对象；
- 生成或复用的正式对象 ID；
- 确认人、确认时间和确认理由；
- 被确认的关系及其证据。

只有“已确认对象”和“已确认关系”才能进入正式资产图谱。

### 阶段 4：前端多视图改造

目标：同一套底层数据服务不同角色，避免老板看到层级后产生困惑。

#### 业务视图

默认给老板和普通使用者，按平台、服务、应用、使用人和费用展示。

#### 六层治理视图

给管理员、IT 和接管人，展示对象层级、关系、责任和缺失项。

#### 原始台账视图

尽量保留老板原系统的表格结构，并在每行增加层级标签、系统对象和待确认状态。

前端原则：

- 层级不是主导航；
- 不展示空层级链路；
- 不强制用户先选择 L4/L5；
- 保留原始名称和业务语义；
- 通过渐进展开查看详细关系；
- 同一对象不因不同视图重复创建。

### 阶段 5：正式入库和生产发布

正式生产入库前必须同时满足：

1. 后端模型迁移已在隔离环境验证；
2. 新版本前后端构建通过；
3. 生产数据库完成备份并核验校验值；
4. 老板和阿里云来源均已确认使用哪一份原始快照；
5. 资料接入池中的候选对象和关系已逐项审核；
6. 已明确本次正式入库范围，不包含未确认的 L4/L5；
7. 完成 dry-run，确认不会新增错误对象或归档既有人工资产；
8. 获得用户对具体批次和具体对象范围的明确授权。

发布后核验：

- MiniMax、DeepSeek 等人工资产仍存在；
- 未确认候选仍可见且未进入正式资产统计；
- L2/L3/L6 数量与确认清单一致；
- 没有明文凭据进入数据库、日志或页面；
- 来源审计、确认人和确认时间可追溯；
- 健康检查保持 ready。

## 五、当前入库判断

现在可以开始准备老板台账和阿里云资料的“接入池候选数据”，也可以在本地或隔离环境验证实例化映射。

当前不应直接写入生产正式资产库，原因是：

- 后端新模型和导入规则尚未部署生产；
- 数据库迁移尚未在生产执行；
- 前端确认界面尚未完成；
- 当前“原本定下的那批实例”仍需明确具体批次和对象范围。

因此，正确顺序是：

> 后端模型收口 → 接入池候选 → 用户逐项确认 → dry-run → 明确授权 → 正式入库 → 前端多视图改造。

本规划文件只作为后续实施依据，不会触发生产写入、归档、删除或部署操作。
