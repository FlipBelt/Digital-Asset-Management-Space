# 集团账号管理中台：重构前版本说明

> 版本冻结日期：2026-08-07
> 用途：用于会议演示重构前系统的能力、局限与本次重构的必要性。

## 1. 旧版的设计目标与已有成果

旧版本以“统一资产底库”为目标，已经完成以下能力：

- 组织、部门、人员同步，并识别部门主管；
- 资产、平台、企业租户、账号、服务实例等基础 CRUD；
- 资产责任人、资产关系、字段扩展、归档与审计；
- 服务用量、流程风险、Excel 导入导出；
- 钉钉内免登身份识别；
- 部署在 ECS，前后端与 PostgreSQL 分离运行。

技术结构为 Vue 3 + Vite 前端、FastAPI 后端、PostgreSQL 数据库、Nginx + systemd 生产部署。旧版本的核心菜单为“工作台、资产中心、平台与账号、组织与人员、服务与用量、流程与风险”。

## 2. 旧版的核心问题

### 2.1 数据对象以技术表为中心，不以用户任务为中心

旧版将平台、企业租户、账号、服务实例和资产分别展示。用户需要先理解内部数据表，才能登记一个简单事实，例如“公司新买了一台阿里云 ECS”。

这造成三个直接问题：

1. 同一件事需要跨多个页面填写；
2. “企业租户”“服务实例”等术语难以理解；
3. 平台账号、注册手机号、RAM 子账号、具体 ECS 等内容混在资产列表中，无法看出层级与归属。

### 2.2 列表优先，无法表达资产之间的真实网络

资产中心是扁平表格。它可以检索记录，但不能直接回答管理中最重要的问题：

- 某个系统运行在哪台服务器、哪一个云账号下？
- 一个平台注册身份绑定了哪些平台账号？
- 哪些人拥有某平台的子账号或订阅授权？
- 某位负责人离职时，需要交接哪些资产和权限？

### 2.3 历史资料进入系统的成本高

公司已有 Excel、文本文件、聊天资料和其他账号管理表。旧版的 Excel 导入偏向固定资产字段，不能保留来源、识别不确定项、处理重复记录或分批确认。

### 2.4 工作台没有按使用者分流

员工、部门主管、IT 资产管理员看到的入口基本一致。普通同事会看到过多与自己无关的底表和配置，导致系统虽然已上线，却难以形成日常使用习惯。

## 3. 重构的总体思路

本次重构不推倒既有系统，而是在已有资产、组织、关系和审计能力上重新组织数据和交互。

### 3.1 用六类业务对象统一模型

1. 公司主体；
2. 注册身份；
3. 平台目录；
4. 公司平台账号；
5. 平台访问账号与授权；
6. 服务、资源与系统。

用户只填写当前要登记的事实。对象之间的关联由表单选择、默认值、快捷新建和后续补充完成，不要求用户先理解底层表结构。

### 3.2 用“资产地图”替代纯表格理解方式

资产地图以公司、平台、公司平台账号、资源/系统为主链路。点击一个节点后，只展开其直接关联和责任信息，使“归属、部署、依赖、授权”可视化。

列表保留为管理员的检索与批量管理工具，不再是用户理解资产的唯一入口。

### 3.3 用资料接入工作台降低首次整理成本

导入功能将支持 Excel/CSV、文本/文件夹、粘贴内容和标准模板。系统先保存原始来源，再给出结构化识别建议；用户确认后才写入正式资产库。由此可以逐步接入各业务部门的授权清单和 IT 管理人员维护的分散资产资料。

### 3.4 按角色组织入口

- 普通员工：我的使用、我的授权、提交发现；
- 部门主管：部门资产、待确认、部门人员授权；
- IT/资产管理员：资产地图、平台与账号、资料接入、治理中心。

## 4. 演示时建议强调的价值

旧版本证明了系统已经具备组织同步、资产入库、关联、审计和部署能力；重构解决的是“真正能被公司使用”的最后一公里：降低录入成本、理清资产网络、支持历史资料接入，并让不同岗位只看到自己需要做的事。
